# Personal edition workflow

This guide documents the personal-use features added on top of the compatible
Vault Format v3 container. The encrypted container schema remains
`{"version": 2, "entries": ...}`; new personal fields use an encrypted,
namespaced entry metadata value so earlier clients can still open the vault.

## Everyday setup

1. In **Settings → Personal security and scheduled backups**, choose a lock
   timeout and enable a backup destination. Use a folder already synchronized
   by OneDrive, Dropbox, Syncthing, or a NAS client for an off-device encrypted
   copy. A backup runs only while Vault Unified is open and unlocked.
2. Save an **Emergency recovery kit** to a different location, then write the
   recovery code down offline. The kit is independently encrypted and needs
   both the file and code. Recovery replaces the active vault under a new
   master password and retains an encrypted pre-recovery copy through the
   normal atomic-write backup path.
3. Set up a remote source only after reviewing its sync preview. Imported
   entries are deliberately local-only until that review is completed.

## Personal entry data

Entries can be labeled as logins, secure notes, cards, identities, SSH keys,
or recovery codes. They support up to 32 custom fields, an optional TOTP
secret, up to ten small inline attachments (1 MiB each; 5 MiB total), and up
to twenty prior field versions. Attachments are intentionally not copied into
history snapshots, so restoring a prior version does not resurrect deleted
binary contents.

These fields are encrypted locally but are not portable synchronization
fields. A remote password-manager adapter therefore cannot overwrite them,
and a normal remote sync will not push them to another provider.

## Transfers

JSON transfers include personal metadata and attachments. CSV transfers omit
attachments and are intended for basic account migration. Both flows require
an explicit confirmation because the transfer content is plaintext. Delete
the exported file as soon as its intended import is complete.

## Chromium extension

The optional extension lives in
[`apps/browser-extension`](../apps/browser-extension). It uses a five-minute
single-use pairing code generated by an unlocked desktop app. The resulting
browser token is held only in browser session storage, is bound to that
extension’s origin, and becomes unusable on desktop lock, desktop exit, after
twelve hours, or after a new pairing code is generated.

The extension looks up only exact website-host matches and receives a password
only after the person opens its popup and chooses a specific entry. It does
not receive the desktop bootstrap secret or master password.

## Mobile access

The desktop sidecar remains loopback-only; exposing it over Wi-Fi would make a
phone connection a new remote-control security boundary. Until a dedicated
end-to-end-encrypted mobile protocol and storage target are selected, use an
already configured Bitwarden or Proton Pass source with that provider’s
official mobile app for portable standard login fields. The personal-only
metadata described above stays on the encrypted desktop vault by design.
